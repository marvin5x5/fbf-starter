fbf-starter · build pipeline plan

Template-driven init: doctrine + tooling ships, the theme is grown

The starter baseline stops carrying a half-built theme. It carries the recipe (templates/), the rules (docs + skills) and the runner (/init-project). The theme files come into existence at init — so there are never stale stubs to mislead anyone.

01What ships vs. what is generated

Committed in the starter

  • templates/ — canonical skeletons (new, source of truth)
  • .claude/skills/init-project/ (new)
  • .claude/skills/{developer,qa,pm,design-to-elementor-wp}/
  • scripts/init.mjs — reduced to a pre-flight check
  • Docs: BUILD-PROCESS.md · CLAUDE.md · README.md · HICCUP-LOG.md · PHASE-READINESS.md
  • package.json · .env.example · .gitignore

Generated by /init-project

  • style.css · functions.php — rendered from templates
  • inc/shortcodes.php · lib/custom-functions.php
  • scss/** — full tree from templates
  • assets/css/main.css — from npm run build:css
  • context.md — fresh per project
  • static-website-reference/ · dev-tools/ — dirs recreated for team uploads
Node (deterministic) Claude-driven Human step

02The pipeline

1
cp .env.example .envhuman Fill in identity, brand tokens, fonts URL.
2
npm installnode Installs sass. Unchanged.
3
/init-projectclaude skill Orchestrates: (a) run init.mjs pre-flight — .env valid, parent theme resolvable · (b) render templates/ → root, substituting {{TOKENS}} · (c) stamp {{CLIENT_NAME}}/{{AGENCY_NAME}} into kept docs · (d) create context.md + upload dirs · (e) npm run build:css · (f) report next steps.
4
Upload design reference → start Developer gatehuman Team drops the approved static site into static-website-reference/; build proceeds Developer → QA → PM.

03templates/ layout & token convention

# {{TOKEN}} placeholders resolved from .env by the skill
templates/
├── style.css              {{CLIENT_NAME}} {{THEME_AUTHOR}} {{PARENT_THEME}}
├── functions.php          {{THEME_HANDLE_PREFIX}} {{GOOGLE_FONTS_URL}}
├── inc/shortcodes.php     verbatim
├── lib/custom-functions.php verbatim
└── scss/
    ├── abstracts/_tokens.scss  {{BRAND_PRIMARY}} {{BRAND_ACCENT}} {{FONT_SANS}} {{FONT_SERIF}}
    ├── abstracts/_mixins.scss  base/*  elementor/_overrides.scss  main.scss  verbatim
    └── components/_header,_nav,_footer,_buttons,_review-popup.scss  stubs → Claude fills from design

04Migration steps (on execute)

  • Create templates/ — git mv current generated files in verbatim, then revert live .env values back to {{TOKEN}} placeholders.
  • Write init-project/SKILL.md — the render / stamp / build orchestration.
  • Reduce init.mjs — drop string-replace; keep .env parse + validation, non-zero exit on bad config.
  • Remove generated files from the baseline (style.css, functions.php, inc/, lib/, scss/, assets/css/main.css, context.md).
  • Update README + BUILD-PROCESS.md; regenerate CLAUDE.md from doctrine so the two don't drift.

05Decisions to settle first

.gitignore the generated files? — Recommend no. "Remove from repo" applies to the starter baseline only; once a project inits you want to commit functions.php, scss/, etc. to that project's repo. Ignoring them would fight real work.
Commit assets/css/main.css? — It is a pure build artifact, so it's a fair gitignore candidate. But current doctrine says "commit main.css after SCSS changes" — keep that unless we're changing the convention too.
